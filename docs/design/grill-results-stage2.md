# TMB: итоги грила по этапу после OpenShell-майлстоуна

Дата: 2026-10-17. Запись решений, одобренных человеком по [issue #4](https://github.com/Vchekryzhov/tmb/issues/4) после вердикта [#10](https://github.com/Vchekryzhov/tmb/issues/10) ([VERDICT-OPENSHELL.md](../../VERDICT-OPENSHELL.md)). Это не спека: спеки пишутся по этой записи отдельно. Нумерация вопросов сохранена, на неё ссылаются ADR 0004 и 0005.

Исходное состояние кода, от которого отталкивались решения: env собирается из `fixed_env` и `allowed_env_keys`, причём фиксированный ключ перебивается запросом; cwd проверяется только на realpath и каталог; целевой uid только 0; исполняемый файл запускается через `/proc/self/fd/N`, cwd передаётся путём; одобрение читается со stdin под общим мьютексом; одобрения живут в памяти; claim-файлы без срока и без очистки; журнал без fsync, ротации и reopen; TLS читается один раз; allowlist по отпечатку сертификата; упаковки нет.

## Разбивка этапа

- **Q1.** Два последовательных майлстоуна. A «политика и харденинг»: очередь одобрений и роль одобряющего, политика cwd и env, TOCTOU для cwd, очистка claim-файлов. B «эксплуатация»: идентичность по ключу и CA, reload, журнал, упаковка и unit, пруф на настоящем хосте.
- **Q18.** #4 остаётся зонтиком: из него рождаются две спеки отдельными issues, #4 закрывается ссылкой на них.
- **Q25.** Порядок тикетов. A: очередь и одобряющий → политика cwd/env → TOCTOU cwd → GC → расширение N-серии. B: SPKI-идентичность и CA → SIGHUP/reload → журнал → nfpm и unit → VM-пруф → вердикт.
- **Q19.** Два ADR: [0004](../adr/0004-approver-role-and-approval-queue.md) одобряющий и очередь, [0005](../adr/0005-requester-identity-by-public-key.md) идентичность по открытому ключу.

## Майлстоун A: политика и харденинг

- **Q2.** Целевой пользователь только root в обоих майлстоунах: `--root` у клиента обязателен, `uid_not_supported` остаётся. Непривилегированные команды агент выполняет сам в песочнице; не-root цель откладывается до запроса.
- **Q3.** `allowed_cwd_roots`: список абсолютных каталогов; realpath запрошенного cwd обязан лежать внутри одного из них, иначе `cwd_not_allowed` до показа одобрения. Пустой список запрещает всё. Пакет по умолчанию даёт `["/tmp"]`. Владелец и права каталога не проверяются: решает человек по показанному realpath.
- **Q4.** Политика окружения: ключ из `fixed_env` нельзя переопределить запросом (`env_fixed_key`); значения без NUL и перевода строки, не длиннее 4 KiB; `PATH` только из `fixed_env`; консоль одобрения показывает итоговое окружение процесса, не окружение запроса.
- **Q5.** TOCTOU: fd каталога cwd удерживается от одобрения до exec, chdir через `/proc/self/fd/N`, как уже сделано для исполняемого файла. Для exe остаётся `/proc/self/fd/N`: `execveat` потребовал бы собственного ForkExec, это новая поверхность. Риск записи в ту же иноду между одобрением и exec принимается и фиксируется в вердикте.
- **Q6.** Очередь одобрений в брокере и подкоманда `tmb approve` через unix-сокет; одобряют только uid из `approver_uids`, отдельного от allowlist запросчиков. `-approval manual` на stdin остаётся режимом стенда. Это точка подключения для #2 и #3.
- **Q13.** `approval_wait_seconds` (по умолчанию 300): дольше запрос в очереди не ждёт, затем `approval_timeout`. Параметр отдельный от TTL токена. Клиент при ожидании блокируется и пишет «waiting for approval» в stderr.
- **Q14.** Канал одобряющего только unix-сокет хоста с SO_PEERCRED, никогда TLS-листенер песочницы. Одобрение показывает запросчика, итоговое окружение, realpath cwd и exe. Из двух одобряющих решает первый, второй видит «already decided».
- **Q11.** Claim-файлы получают `expires_at`; брокер удаляет файлы старше TTL плюс 24 часа при старте и по таймеру; nonce-файлы так же. Переигровка внутри TTL отклоняется и после рестарта, как сейчас.

## Майлстоун B: эксплуатация

- **Q7.** Идентичность запросчика на пути песочницы это SHA-256 от открытого ключа (SPKI), а не от сертификата: ключ живёт долго, сертификат перевыпускается коротким, allowlist не меняется. Сертификат песочницы живёт до 7 дней.
- **Q8.** Минимальный CA внутри `tmb-broker` (`ca init | issue-server | issue-sandbox`), stdlib, ключ CA на хосте под root. Брокер перечитывает серверный сертификат и CA по SIGHUP и отдаёт сертификат через `GetCertificate`. Внешний CA вне скоупа, PEM стандартный.
- **Q15.** Приватный ключ песочницы рождается внутри песочницы (`tmb keygen`) и не покидает её; на хост уходит открытый ключ или CSR. Чтение ключа другими процессами песочницы остаётся риском и фиксируется в вердикте.
- **Q16.** `allowed_requester_fps` переименовывается в `allowed_requester_keys` без обратной совместимости; конфиг остаётся одним JSON-файлом; флаги `-tls-*` убираются. Пакет ставит `/etc/tmb/config.json.example`, сервис без конфига не стартует.
- **Q20.** Отпечаток попадает в allowlist правкой конфига; брокер перечитывает allowlist и `approver_uids` по SIGHUP (`systemctl reload`); запросы в очереди и одобрения переживают reload. Автоматического добавления по CSR нет: добавление в allowlist это решение человека.
- **Q21.** Сроки: CA 10 лет, серверный сертификат 1 год, сертификат песочницы 7 дней; перевыпуск на тот же ключ. Истёкший сертификат даёт транспортный отказ, не `deny` в журнале. Отзыва нет: удаление отпечатка из allowlist и есть отзыв.
- **Q10.** Журнал: fsync на каждое событие, reopen по SIGHUP, конфиг `logrotate` в пакете, ошибка записи журнала закрывает приём новых запросов. Консьюмер (Alloy → Loki) только сценарий пруфа, не код брокера.
- **Q22.** Каждое событие несёт `schema: 1`; изменение набора полей существующего события поднимает версию; `docs/audit-schema.md` перечисляет события и поля и проверяется lint-тестом против кода.
- **Q9.** deb и rpm через nfpm (YAML один, инструмент пинится в `ci/`), amd64 и arm64; пути `/etc/tmb/config.json`, `/var/lib/tmb`, `/var/log/tmb`, `/run/tmb`; публикация в GitHub Releases по тегу. Клиент `tmb` отдельным бинарником для Linux и macOS.
- **Q17.** Клиент для macOS: tarball в Releases; Homebrew-tap позже.
- **Q24.** systemd unit: `Type=simple`, `User=root`, `RuntimeDirectory=tmb`, `StateDirectory=tmb`, `LogsDirectory=tmb`, `Restart=on-failure`, `KillMode=process`. Sandboxing systemd (`ProtectSystem`, `PrivateTmp`, `ProtectHome`) не применяется: брокер запускает произвольные одобренные команды, им нужен весь хост. `KillMode=process` сохраняет fail-closed без обрыва уже одобренной работы при рестарте брокера.
- **Q12, Q23.** Пруф на настоящем хосте: одноразовая Lima-VM на Mac, Ubuntu LTS arm64, внутри установка `.deb`, `systemctl start tmb-broker`, OpenShell gateway, песочница, `tmb approve` во второй сессии. Харнесс `harness/run-vm.sh` с реестром V-серии в `ci/scenarios/`. rpm проверяется только установкой в контейнере Fedora. omen как ручная проверка после. Docker-стенды остаются как регрессия.

## Вне скоупа этапа

- Не-root целевой пользователь.
- Внешний CA, CRL и OCSP.
- Автоматический анроллмент по CSR.
- Systemd-sandboxing брокера.
- Homebrew-tap для клиента.
- Подписант с Touch ID ([#2](https://github.com/Vchekryzhov/tmb/issues/2)) и удалённое одобрение ([#3](https://github.com/Vchekryzhov/tmb/issues/3)): подключаются к очереди одобрений как варианты одобряющего, сами не реализуются.
