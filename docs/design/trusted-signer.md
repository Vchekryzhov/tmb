# Доверенный подписант TMB: исследование и черновик дизайна

Дата: 2026-10-31. Статус: черновик для [issue #2](https://github.com/Vchekryzhov/tmb/issues/2); решения владельца по вопросам В1–В12 записаны в [ADR 0006](../adr/0006-trusted-signer-touch-id.md). Это не ADR и не спека: документ раскладывает варианты, факты платформы и вопросы владельцу; связанный канал удалённого одобрения это [issue #3](https://github.com/Vchekryzhov/tmb/issues/3).

## Исходная точка

Одобрение живёт в брокере ([ADR 0004](../adr/0004-approver-role-and-approval-queue.md)): запрос, прошедший политику, ждёт в очереди одобрений не дольше `approval_wait_seconds`; одобряющий (uid из `approver_uids`, SO_PEERCRED на unix-сокете хоста) получает `list` и отвечает `decide` с `item_id`, `item_hash` и решением; брокер сверяет хеш, запрещает решать свой запрос и выдаёт одноразовый токен с `token_ttl_seconds` (60 по умолчанию), который гасится при предъявлении. Подписант по ADR 0004 подключается к той же очереди как вариант одобряющего.

Что в коде важно для подписанта (`src/internal/proto/proto.go`, `src/cmd/tmb-broker/queue.go`):

- `QueueItem.Hash` это `Request.Hash()`, SHA-256 от канонического JSON запроса (путь исполняемого файла из запроса, argv, cwd из запроса, uid, окружение запроса, nonce). Показ одобрения при этом содержит другие значения: realpath исполняемого файла и cwd, итоговое окружение процесса. Подпись только над `Hash` не доказывает, что человек видел именно показанные поля.
- В `QueueItem` нет хоста: одобряющий сегодня всегда сидит на том же хосте, поэтому имя хоста подразумевается. Подписант на Mac одобряет для нескольких хостов, и хост обязан войти в подписываемые данные.
- В `QueueItem` нет срока: `QueuedAt` есть, крайний срок решения брокер держит у себя.
- Решение аутентифицирует только канал (uid одобряющего). Криптографического доказательства решения нет: кто получил uid одобряющего на хосте, тот одобряет.

Требования #2, которые дизайн обязан закрыть: показ точных данных, которые подписываются (хост, пользователь выполнения, абсолютный путь программы, упорядоченный argv, id запроса, время выдачи и истечения, TTL 60 секунд); показанное и подписанное совпадают без подмены; одно касание Touch ID даёт ровно одно подписанное решение; отмена, таймаут и ошибка аутентификации дают отказ; нет обходного пути подписи непрозрачных данных; проверка подписи и погашение остаются на принимающей стороне, UI и биометрия их не заменяют. Файловый ключ, доступный агенту, допустим только в изолированных тестах с фейковым подписантом.

## Факты платформы

Сверено по первоисточникам, ссылки в разделе «Источники». Пометка «проверить в прототипе» означает, что документация не даёт однозначного ответа.

Secure Enclave и ключи:

- Secure Enclave работает только с ключами NIST P-256 (ECDSA-подпись и ECDH); ключевой материал в открытом виде нельзя ни ввести в SE, ни вывести из него, ключом пользуется только тот SE, который его создал. Подпись это обычная ECDSA P-256 над SHA-256, её проверяет `crypto/ecdsa` из stdlib Go: брокер остаётся stdlib-only.
- Доступ к ключу задаёт `SecAccessControl` с флагами: `.privateKeyUsage` (обязателен для SE), `.userPresence`, `.biometryAny`, `.biometryCurrentSet` (ключ непригоден, пока набор отпечатков отличается от набора при создании), `.devicePasscode`, `.companion`, комбинаторы `.and` и `.or`. Каждая операция без контекста создаёт новый контекст и показывает лист аутентификации; операция с уже аутентифицированным `LAContext` (`kSecUseAuthenticationContext`) проходит без запроса.
- Отсюда правило одного касания: один `LAContext` на одну подпись и `invalidate()` сразу после неё; после `invalidate()` контекст даёт `LAError.invalidContext`. Опасна именно повторная передача аутентифицированного контекста. `touchIDAuthenticationAllowableReuseDuration` (по умолчанию 0, максимум «до пяти минут») относится только к недавней разблокировке устройства Touch ID, не к аутентификации keychain, но и его подписант оставляет нулевым.
- Ключ хранится одним из двух способов. Первый: `CryptoKit.SecureEnclave.P256.Signing.PrivateKey` и его `dataRepresentation`, непрозрачный блоб в файле, пригодный только на этом SE. Проверено на этом Mac (macOS 26.5): бинарник `swiftc` с подписью ad-hoc, без entitlements и без бандла создал ключ, сохранил блоб (284 байта), восстановил его и подписал с успешной проверкой. Так же устроен `age-plugin-se`, обычный CLI из Homebrew (генерация ключей с macOS 14). Второй: постоянный элемент data protection keychain; тот же ad-hoc CLI получает `-34018` (`errSecMissingEntitlement`) при `kSecAttrIsPermanent=true`. Keychain access group берётся из entitlement, подтверждённого provisioning profile, в бандле вида приложения (TN3137); одной подписи Developer ID мало.
- Блоб из файла может загрузить любой процесс того же пользователя и попросить подпись над своими данными (системный лист покажет его имя приложения и его строку причины); проверить в прототипе. Keychain access group ограничивает использование ключа приложениями своей группы.
- Оба способа работают только в контексте пользователя с GUI-входом: launchd-демон уровня системы SE так не использует.

Touch ID и UI:

- Системный лист Touch ID называет приложение и показывает строку причины (`localizedReason`), которую задаёт само вызывающее приложение. Публичного API доверенного показа (аналога Android Protected Confirmation) на macOS нет. Ближайшее это secure intent, физическая связь кнопки или Touch ID с SE, но Apple ограничивает его Apple Pay и сопряжением Magic Keyboard; сторонним приложениям он недоступен. Значит, Touch ID подтверждает присутствие человека у Mac, а не то, что он прочитал; соответствие показа и подписи обеспечивает только целостность процесса подписанта.
- `deviceOwnerAuthenticationWithBiometrics` без системного отката на пароль (после серии неудач кнопка возврата даёт `LAError.userFallback`, биометрия блокируется до ввода пароля); `deviceOwnerAuthentication` допускает биометрию, Apple Watch и пароль пользователя; варианты `...WithBiometricsOrCompanion` и `...WithCompanion` есть с macOS 15, варианты `...Watch` устарели. Выбор политики это выбор владельца (вопрос В5).
- Поведение LocalAuthentication в SSH-сессии на Mac Apple не документирует; документирован только `LAError.notInteractive` при запрете интерфейса. `pam_tid.so.2` на этом Mac содержит строки «Aqua» и «unable to determine session», то есть требует Aqua-сессии; README `pam_reattach` подтверждает, что `pam_tid` не спрашивает по SSH, а в tmux и screen теряет сессию входа. `/etc/pam.d/sudo_local` переживает обновления системы (так говорит шаблон `sudo_local.template` на этом Mac). Для подписанта это значит: он работает только в локальной сессии пользователя, отсутствие GUI даёт отказ, не обходной путь; проверить в прототипе.
- `LARight` и `LAPersistedRight` (macOS 13 и новее) это обёртка над тем же SE-ключом и access control: операции с ключом доступны после `authorize(localizedReason:)` и до `deauthorize()`, то есть сессионно, а не на одну операцию, и с подписываемыми данными не связаны. Для одного касания на одну подпись они не сильнее `SecAccessControl` с отдельным контекстом.

Подпись кода и распространение:

- CLI с блобом `dataRepresentation` работает с подписью ad-hoc (проверено). Хранение в keychain требует приложения с provisioning profile; для распространения вне App Store ещё и Developer ID с нотаризацией. Общее правило Apple DTS «доступ к SE требует App ID из профиля» на практике бьёт по ключам в keychain, не по блобам CryptoKit.
- Teleport пришёл к тому же: Touch ID в `tsh` требует подписанной и нотаризованной сборки из официального `.pkg`; сборки из Homebrew и из исходников Touch ID не поддерживают.
- step-kms-plugin (`mackms`) создаёт SE-ключи только в бинарнике, подписанном с нужными entitlements; параметр `bio` задаёт `privateKeyUsage` вместе с `biometryCurrentSet`.

Как это делают другие:

| Проект | Где ключ | Что показывает человеку | Что подписывает | Вывод для TMB |
| --- | --- | --- | --- | --- |
| Secretive | SE, отдельное приложение-агент | в листе Touch ID приложение-запросчик (по PID пира сокета) и имя ключа; `user@host` только в уведомлении после подписи; есть окно повторного использования аутентификации | данные SSH-клиента без изменений | показ после подписи и подпись присланных данных: ровно то, что #2 запрещает |
| Teleport (`tsh`, per-session MFA) | SE через подписанный и нотаризованный `tsh` | факт входа или новой сессии | WebAuthn-assertion сервера | подпись приложением с entitlement; одно касание на сессию, не на команду |
| step-kms-plugin (`mackms`) | SE в подписанном бинарнике, URI с `se=true` и `bio=true` | ничего, кроме системного листа | произвольные данные | годится как бэкенд подписи, не как доверенный показ |
| macOS sudo и `pam_tid` | биометрия без ключа | имя процесса и «sudo» | ничего | гейт без криптографического доказательства; это вариант Б ниже, отвергнутый в [ADR 0001](../adr/0001-oneshot-ssh-certificates.md) пункт 3 |

Общий вывод: ни один из готовых инструментов не связывает показ конкретной команды с подписью; это и есть собственная работа #2.

## Варианты архитектуры

### А. Подписанное решение: SE-ключ подписывает данные запроса, брокер проверяет

Брокер строит для каждого элемента очереди канонический байтовый payload одобрения. Подписант на Mac получает эти байты, разбирает их строгим декодером, показывает каждое поле из разобранной структуры, после Touch ID подписывает ровно полученные байты ключом SE и отправляет `decide` с подписью. Брокер проверяет подпись над своими же байтами (подписанту не нужно присылать payload обратно) открытым ключом из нового перечня ключей одобряющих и только затем выдаёт токен. Подпись становится доказательством решения в журнале.

- Плюсы: брокер проверяет криптографию, а не только канал; uid одобряющего на хосте сам по себе больше не одобряет; закрывает требование #2 «приёмный шлюз проверяет подпись и поля»; payload переносим по любому каналу, что развязывает #2 и #3.
- Минусы: меняется протокол и брокер; появляется анроллмент ключей одобряющих; подписант на Swift это новый язык и новая сборка в репозитории.

### Б. Touch ID только как гейт локального UI

Приложение на Mac показывает запрос, вызывает `LAContext.evaluatePolicy` и при успехе шлёт обычный `decide` через существующий канал одобряющего. Брокер не меняется.

- Плюсы: минимум изменений, работает с сегодняшней очередью.
- Минусы: брокер не получает доказательства; любой, кто получил канал одобряющего (SSH-ключ на Mac, uid на хосте), одобряет без касания; это ровно слабость, описанная в ADR 0001 пункт 3. Не закрывает «UI и биометрия не заменяют проверку». Годится только как промежуточный шаг для UX.

### В. Аппаратный FIDO-ключ вместо SE

Payload подписывается U2F/FIDO2-ключом (у владельца есть Rutoken U2F): challenge это хеш payload, касание ключа это присутствие. Брокер проверяет подпись U2F (P-256, stdlib).

- Плюсы: ключ отделён от Mac, работает и без биометрии, не зависит от Apple-подписи кода.
- Минусы: у U2F нет биометрии и нет показа; показ всё равно в приложении на Mac; нужен `libfido2` или собственная реализация CTAP поверх HID, это внешняя зависимость или большой объём кода; формат подписи U2F (данные приложения и счётчик) усложняет проверку.

### Г. Подписанное разрешение без очереди

Подписант выпускает автономное разрешение, которое агент предъявляет брокеру сам, как в [итогах грила](grill-results.md) (сценарий «разрешение уже предъявлено» из #3). Брокер проверяет подпись и гасит id.

- Плюсы: брокеру не нужно ждать живого одобряющего.
- Минусы: противоречит ADR 0004 (одобрение через очередь), требует, чтобы агент передал запрос подписанту в обход брокера, и тогда показ строится из данных агента, не из разрешённых брокером realpath и итогового окружения. Сохраняется как будущий вариант для #3, не для #2.

Рекомендация черновика: вариант А как цель, вариант Б допустим только как временный UX-прототип без заявлений о безопасности. Выбор за владельцем (вопрос В1).

## Совпадение показанного и подписанного (вариант А)

- Источник байтов один: брокер. Подписант не собирает payload из полей, а получает готовые байты, разбирает их и рисует из результата разбора. Подписывается исходный массив байтов, не повторная сериализация.
- Канонизация с проверкой: подписант отклоняет payload, если повторная сериализация разобранной структуры не совпадает с полученными байтами (дубликаты ключей, лишние поля, другой порядок, нормализация Unicode). Это то же правило, что `DecodeRequest` с `DisallowUnknownFields`, только строже.
- Разделение доменов: payload начинается с фиксированного префикса вроде `tmb-approval-v1` и нулевого байта, поэтому подпись нельзя использовать ни для SSH, ни для другой версии формата, и наоборот.
- Состав payload (предложение): версия формата; идентичность хоста (имя из конфига брокера и отпечаток его серверного ключа); id элемента очереди и полный хеш запроса; случайный challenge брокера на элемент; идентичность запросчика; целевой uid и имя пользователя; realpath исполняемого файла с dev/ino закрепления; упорядоченный argv; realpath cwd; итоговое окружение; nonce; время постановки в очередь; крайний срок решения; TTL токена.
- Показ argv: каждый аргумент отдельной строкой с индексом и длиной; управляющие символы, символы bidi, нулевой ширины и не-ASCII показываются экранированными с явной меткой; пустой аргумент виден как пустой; длинный аргумент показывается полностью с прокруткой, без обрезки. Если какое-то поле нельзя показать целиком, подписант отказывает. Проверки на «необычные argv» из #2 строятся по этому списку.
- Строка `localizedReason` содержит короткий id элемента и хоста, чтобы системный лист и окно подписанта можно было сопоставить. Это помощь человеку, не гарантия: строку задаёт приложение.
- Окно подписанта модальное для одного элемента: пока показан элемент, данные не меняются; новый элемент открывает новое окно; подпись привязана к элементу, показанному в момент касания.

## Одноразовость и сроки

- Одно касание даёт одну подпись: новый `LAContext` на каждую подпись, `invalidate()` после, аутентифицированный контекст никуда больше не передаётся; ключ создан с `.privateKeyUsage` и флагом биометрии. Проверяется в прототипе: две подписи подряд дают два листа Touch ID.
- Одна подпись даёт одно решение: payload несёт challenge брокера на конкретный элемент; элемент покидает очередь на первом решении (`decide` уже так работает); подпись с чужим challenge, хостом или хешем отклоняется до выдачи токена.
- Сроки: окно решения ограничено `approval_wait_seconds`, срок токена `token_ttl_seconds` от проверенного решения. Требование #2 «TTL 60 секунд в подписанных данных» закрывается тем, что TTL токена входит в payload и брокер не выдаёт токен дольше подписанного. Нужно ли подписанту ставить своё время подписи и как жить с расхождением часов Mac и хоста, это вопрос В6.
- Погашение остаётся там же, где сейчас: токен гасится при предъявлении атомарно и через перезапуск. Подпись не заменяет погашение и сама его не делает.
- Отмена, таймаут листа Touch ID, ошибка аутентификации, смена набора отпечатков (`biometryCurrentSet`) и отсутствие GUI дают отказ подписанта; в очередь уходит явный `deny` или ничего (тогда запрос истекает по `approval_timeout`). Какой из двух, вопрос В7.

## Транспорт до брокера (связь с #3)

Payload переносим, поэтому канал выбирается отдельно и не влияет на криптографию.

1. SSH с Mac на хост и существующий канал одобряющего: подписант запускает на хосте `tmb approve` (в машинном режиме) через SSH, получает очередь, отправляет подписанный `decide`. Брокер не меняет листенеры; ADR 0004 «канал одобряющего только локальный» остаётся буквально верным. Минусы: нужен SSH-доступ человека к каждому хосту и uid одобряющего там; опрос очереди или долгоживущая сессия.
2. Отдельный TLS-листенер одобряющего в брокере с mTLS по ключу одобряющего, по образцу [ADR 0003](../adr/0003-sandbox-transport-tcp-mtls.md) и [ADR 0005](../adr/0005-requester-identity-by-public-key.md): Mac подключается к брокеру напрямую. Меняет ADR 0004, требует нового ADR; листенер одобряющего не должен совпадать с листенером песочницы.
3. Посредник (relay, push): хост публикует запрос, Mac забирает. Это и есть вопрос #3, здесь не решается.

Рекомендация черновика: для прототипа #2 вариант 1, он не трогает брокерные листенеры. Выбор канала для эксплуатации это #3 (вопрос В8).

## Модель угроз

Активы: право запустить команду root на хосте; ключ одобряющего в SE; целостность показа.

| Противник | Что может | Что его останавливает | Остаточный риск |
| --- | --- | --- | --- |
| Агент в песочнице на хосте | слать произвольные запросы через точку входа | политика брокера, очередь, показ и касание; подписи у него нет | социальная инженерия: правдоподобная вредная команда, которую человек одобрит |
| Код с uid одобряющего на хосте | слать `decide` | в варианте А `decide` без валидной подписи отклоняется | в варианте Б одобряет без касания |
| Сеть между Mac и хостом | перехват, повтор, подмена | канал (SSH или mTLS) плюс подпись над challenge брокера и хостом | отказ в обслуживании: одобрение не доходит, запрос истекает |
| Код того же пользователя на Mac | вызвать ключ, нарисовать фальшивое окно, кликать в UI | касание пальцем; ключ в keychain access group недоступен чужим приложениям | при ключе-блобе в файле этот код подпишет свой payload с фальшивым показом, если человек коснётся (проверить в прототипе) |
| Root на Mac или подмена приложения подписанта | управлять показом и числом подписей за касание, подменить байты между показом и подписью | ключ не извлекается из SE и не используется без касания | принимается: компрометация Mac равна компрометации одобряющего; смягчение это второе устройство и политика брокера, см. ADR 0006 |
| Скомпрометированный брокер | показать подписанту одно, выполнить другое | ничего: брокер и есть исполнитель | вне модели: брокер root на хосте |

Дополнительно: потеря или смена отпечатков делает ключ непригодным (`biometryCurrentSet`), восстановление это новый ключ и новый анроллмент; кража Mac без отпечатка не даёт подписи; утечка открытого ключа ничего не даёт.

## Изменения в протоколе и брокере (вариант А, предложение)

`src/internal/proto`:

- Новый тип `ApprovalPayload` с канонической сериализацией и префиксом домена; функция построения байтов и строгий разбор с проверкой «сериализация разобранного равна исходным байтам». Тот же код используется фейковым подписантом в тестах.
- `QueueItem` получает поля хоста, challenge, крайнего срока решения и TTL токена, либо готовые байты payload (base64) рядом с текущими полями.
- `Request` для `decide` получает `Signature` (DER ECDSA) и `ApproverKey` (отпечаток SPKI). Поле, неизвестное старому брокеру, им отклоняется (`DisallowUnknownFields`): смешивать старый брокер и новый подписант нельзя, это ожидаемо, протокол без версии.

`src/cmd/tmb-broker`:

- Конфиг: `host_id`; `approver_keys` (отпечатки SPKI P-256 ключей одобряющих с именем); режим `require_signed_decision`. Перечитывается по SIGHUP, как `approver_uids`.
- `queueApproval` генерирует challenge и строит payload при постановке в очередь; `decide` проверяет отпечаток ключа по allowlist, подпись над сохранёнными байтами, срок и только потом передаёт решение. Новые коды отказа: `signature_required`, `signature_invalid`, `approver_key_unknown`, `decision_expired`.
- Журнал: событие `approval` получает отпечаток ключа и подпись; `docs/audit-schema.md` и версия схемы событий меняются вместе.
- Ни выдача токена, ни погашение, ни закрепление exe и cwd не меняются.

Клиент `tmb approve`: машинный режим вывода очереди и ввода подписанного решения для подписанта (если выбран транспорт 1).

## План прототипа

1. Спайк на Swift в `prototype/` (не продукт): создать SE-ключ с `.privateKeyUsage` и `.biometryCurrentSet`, экспортировать открытый ключ, подписать байты. Замерить: лист Touch ID на каждую подпись с новым контекстом; поведение отмены, таймаута, блокировки биометрии; запуск по SSH на Mac и из LaunchAgent; может ли другой процесс того же пользователя подписать ключом-блобом; CLI с подписью ad-hoc против приложения Developer ID с keychain access group.
2. Совместимость с Go: подпись SE проверяется `crypto/ecdsa.VerifyASN1` над SHA-256 из stdlib; тестовые векторы из спайка в тесты `proto`.
3. Протокол и брокер по разделу выше с фейковым подписантом (ключ P-256 в файле, только в тестах), новые сценарии N-серии: верная подпись; подпись чужого элемента, хоста, challenge; просроченное решение; неизвестный ключ; неподписанный `decide` при `require_signed_decision`; повтор подписи.
4. Минимальное SwiftUI-приложение: окно показа, Touch ID, подпись, отправка через SSH. Ручная проверка на Mac по списку из #2, без правок системного sudo и PAM; протокол ручной проверки в репозитории.
5. Вердикт этапа и ADR по решениям владельца.

## Решения: см. ADR 0006

Вопросы В1–В12 этого черновика закрыты владельцем 2026-10-31/11-01; ответы и мотивировка в [ADR 0006](../adr/0006-trusted-signer-touch-id.md). Коротко: вариант А; ключ блобом в файле; приложение в строке меню на Swift в `signer/`; только биометрия; сроки задаёт брокер; отказ это явный неподписанный `deny`; транспорт прототипа SSH; `require_signed_decision` глобально; хост это имя плюс отпечаток серверного ключа с TOFU на Mac; анроллмент вручную по образцу ADR 0005; realpath cwd и итоговое окружение подписываются обязательно.
