# ADR 0001: Одноразовые SSH-сертификаты с force-command для привилегированных команд агента

Дата: 2026-10-04. Статус: отклонено 2026-10-06 по итогам аудита, суперседено [ADR 0002](0002-standalone-tmb-broker.md).

Документ восстановлен 2026-10-16 из истории (удалён коммитом `e575551`), чтобы причины отказа были объяснимы. Раздел «Решение» сохранён как был; раздел «Почему отклонено» добавлен при восстановлении.

## Контекст

Агенты opencode выполняют команды в неинтерактивном bash (stdin отключён), поэтому sudo с паролем невозможно: команда падает с «a terminal is required to read the password». Нужен способ давать агентам привилегии только с явного биометрического участия человека (Touch ID на MacBook) на трёх поверхностях: локальный Mac, omen_local (Ubuntu), NAS (Synology DSM 7). Требования: показ полной команды до выполнения; одно касание на команду; без паролей в чате; настройка хостов без хардкода.

## Решение (отклонено)

- **Локальный Mac**: `/etc/pam.d/sudo_local` с `pam_tid.so` (переживает обновления macOS) плюс `Defaults timestamp_timeout=0`: касание на каждую sudo-команду, без кэша. Показ команды в ask-диалоге opencode.
- **Удалённые хосты**: короткоживущий SSH-сертификат (TTL около 60 секунд) с force-command, вшитой в сертификат, и principal=root. CA-ключ в Secure Enclave Mac (Secretive); `ssh-keygen -U` подписывает сертификат через агент, Touch ID на каждую подпись. На хостах: `TrustedUserCAKeys` и `PermitRootLogin forced-commands-only`. sudo на хостах не используется вовсе.
- **Оболочка `tmb <host> <command...>`**: единая точка, показ команды, подпись, выполнение, запись в журнал.

Рассмотренные тогда альтернативы: sudoers NOPASSWD-allowlist (полномочия не истекают, правки на каждом хосте), Teleport / Vault / step-ca (отдельный сервер ради двух домашних хостов), touchid-remote (не работает на DSM), собственный подписывающий демон (казался лишним при наличии Secretive).

## Почему отклонено

Аудит 2026-10-06 сверил обещания README и issue #1 с документацией OpenSSH. Механизм работает: OpenSSH подписывает force-command внутри сертификата, `ssh-keygen -U` штатно использует CA через агент. Отклонены дополнительные гарантии, которые схеме приписали.

1. **«Ровно один раз» не обеспечивается.** Сертификат с соответствующим приватным ключом можно предъявлять повторно весь TTL: sshd не помнит, что сертификат уже использован, отзыв возможен только через KRL. Истечение TTL не останавливает уже запущенную команду. Настоящий one-shot требует, чтобы принимающая сторона атомарно гасила разрешение до запуска, то есть состояния на хосте. Это и есть брокер.
2. **Нет привязки к хосту.** Если NAS и omen доверяют одному CA и принимают principal `root`, сертификат, выданный для одного, сработает на другом. Лечится отдельными CA или host-specific principals, но это отдельная конструкция поверх sshd.
3. **Touch ID подтверждает использование ключа, а не понимание команды.** Secretive показывает «ключ использован»; команду показывает opencode в другом окне. Показ и подпись независимы, агент может показать одно и подписать другое. Показ точного запроса и подпись должны происходить в одном доверенном компоненте (отсюда [issue #2](https://github.com/Vchekryzhov/tmb/issues/2), доверенный подписант).
4. **force-command фиксирует строку, не поведение.** Содержимое скрипта или интерпретатора и stdin в подпись не входят. В брокере это закрыто pin исполняемого файла по dev/ino и закрытым stdin.
5. **Fallback «CA-ключ на диске плюс биометрическая обёртка» обходится.** Агент, способный прочитать ключ, подписывает напрямую, минуя Touch ID.

Практическое: правка `sshd_config` на DSM затирается обновлениями, а ошибка в ней запирает SSH на хосте.

Что осталось верным и перенесено дальше: контракт разрешения (хост, пользователь выполнения, абсолютный путь, упорядоченный argv, срок, не более одной попытки запуска) сохранён в [итогах грила](../design/grill-results.md) и в ADR 0002. Если к sshd-варианту когда-нибудь вернуться, закрывать придётся пункты 1–4 сразу, и после пункта 1 на хосте всё равно появится компонент с состоянием.
