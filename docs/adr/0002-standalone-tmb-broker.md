# ADR 0002: TMB как отдельный привилегированный брокер, sudo не затрагивается

Дата: 2026-10-09.

## Контекст

TMB задуман как посредник привилегированного выполнения для AI-агента с человеческим одобрением. Пароль sudo агенту не передаётся. Человеческий sudo и действующая политика sudoers обязаны остаться нетронутыми.

Точка встраивания проверялась двумя экспериментами и одним PoC, все факты ниже подтверждены прогонами.

1. Эксперимент 1 (ветка `prototype/sudo-integration`): python approval-плагин sudo работает, sudoers остаётся политикой, 44+4 проверок PASS. Но плагин требует пересборки sudo из исходников с `--enable-python`, ни один проверенный дистрибутив не собирает python-плагин.
2. Эксперимент 2 (прерван, findings валидны): native C approval-плагин технически возможен, approval API входит в ядро sudo >= 1.9, плагин подключается внешней .so через `/etc/sudo.conf`. Но подтверждено экспериментально: любая строка `Plugin` в sudo.conf делает плагин зависимостью каждого вызова sudo. Битый или недоступный .so валит весь sudo на хосте, включая человеческий парольный путь, с exit 1. Для распространяемого продукта это недопустимый failure domain.
3. PoC 3 (ветка `prototype/tmb-broker`): отдельный привилегированный tmb-broker на Unix socket, 56/56 проверок PASS, нулевая связанность с sudo.

Из трёх проверенных точек встраивания только брокер даёт распространяемый продукт: без пересборки sudo и без расширения failure domain на человеческий путь.

## Решение

TMB это отдельный привилегированный демон-брокер на Unix socket `/run/tmb/tmb.sock` (0660), полностью ортогональный sudo: ноль строк `Plugin`, ноль правок sudoers и PAM.

- Агент живёт в sandbox. MVP-стенд: unprivileged контейнер с `--network none`.
- Целевой sandbox-слой: NVIDIA OpenShell, исследование подтвердило совместимость. Рекомендован вариант B: единственный TCP/MCP endpoint, разрешённый одним правилом `network_policies`. Вариант A, bind-mount одного unix-сокета, остаётся запасным.
- Клиент tmb не исполняет команды. Он шлёт брокеру структурированный запрос: absolute executable, точный упорядоченный argv, cwd, uid, nonce.
- Брокер проверяет uid запросчика через SO_PEERCRED против allowlist. Одобрение человека привязано к точному запросу, а не к диалогу агента.
- Одобренный запрос получает one-shot токен с TTL. Токен и nonce гасятся до запуска через `O_CREAT|O_EXCL` + fsync, погашение переживает рестарт брокера.
- Затем следует ровно один прямой execve: без `sh -c`, без PATH-поиска, env только из allowlist брокера, executable пинится dev/ino, stdin подключён к `/dev/null`, дескрипторы с CLOEXEC.
- Fail-closed только для агентного пути: смерть брокера закрывает агенту доступ, команда не запускается. Человеческий sudo, ssh и OS не затронуты.
- Криптографические подписи с Touch ID и удалённый транспорт являются следующими этапами (issues #2 и #3) и не входят в это решение.

## Статус

Принято (2026-10-09). Суперседает направление sudo-интеграции; эксперименты сохранены как первоисточники на ветках `prototype/sudo-integration` и `prototype/tmb-broker`. Ранее удалённый ADR 0001 об SSH-сертификатах не восстанавливается, нумерация продолжается с 0002.

## Последствия

Положительные:

- sudo неприкосновенен. Failure domain TMB ограничен агентным путём: что бы ни случилось с брокером, человеческий sudo, ssh и OS продолжают работать.
- Деплой обычным пакетом или сервисом, без пересборки sudo из исходников.
- Одобрение и аудит живут в одном месте, в JSONL-логе брокера.

Отрицательные и риски:

- Новый привилегированный демон создаёт новую поверхность атаки. Аутентификация на сокете beyond SO_PEERCRED и права на файл сокета являются обязательной работой MVP.
- Остаточные риски зафиксированы в VERDICT-BROKER.md: окно TOCTOU между stat и execve, symlink-гонки cwd, однохостовой scope.
- OpenShell 0.1.x молод, API churn реален; версии пинуются.
- Подписанная модель разрешений из grill-results переносится на будущий этап, remote-путь issue #3. Контракт полей сохраняется как основа.
