# ADR 0006: Доверенный подписант с Touch ID, подписанное решение проверяет брокер

Дата: 2026-11-01. Расширяет [ADR 0004](0004-approver-role-and-approval-queue.md): подписант это вариант одобряющего, очередь одобрений и канал одобряющего не меняются; добавляется криптографическое доказательство решения. Фиксирует решения владельца по вопросам В1–В12 из [черновика дизайна](../design/trusted-signer.md) для [#2](https://github.com/Vchekryzhov/tmb/issues/2).

## Контекст

Сегодня решение одобряющего аутентифицирует только канал: `decide` принимается от процесса с uid из `approver_uids` на unix-сокете хоста (SO_PEERCRED). Кто получил этот uid на хосте, тот одобряет; брокер не получает доказательства, что человек видел запрос и согласился. Issue #2 требует другого: человек видит точные данные запроса на доверенном устройстве, одно касание Touch ID даёт ровно одно подписанное решение, принимающая сторона проверяет подпись и поля сама, а отмена, таймаут и ошибка аутентификации дают отказ.

Факты платформы, на которые опирается решение (сверены в черновике): Secure Enclave хранит только ключи P-256 и подписывает ECDSA над SHA-256, что проверяется `crypto/ecdsa` из stdlib Go; доступ к ключу задаётся `SecAccessControl`, и флаг `biometryCurrentSet` делает ключ непригодным после смены набора отпечатков; один `LAContext` на одну подпись даёт один лист Touch ID на одно касание; доверенного показа (аналога Android Protected Confirmation) на macOS для сторонних приложений нет, поэтому Touch ID доказывает присутствие человека у Mac, а соответствие показа и подписи обеспечивает только целостность процесса подписанта; ключ как блоб `dataRepresentation` работает в бинарнике с подписью ad-hoc, а ключ в keychain требует бандла с provisioning profile и аккаунта Apple Developer.

Показ одобрения сегодня содержит не те значения, что входят в `Request.Hash()`: показываются realpath исполняемого файла и cwd и итоговое окружение, а хеш считается от путей и окружения из запроса. Подпись над одним лишь хешем не доказала бы, что человек видел показанные поля. В `QueueItem` нет ни хоста, ни крайнего срока: одобряющий всегда сидел на том же хосте, а подписант на Mac одобряет для нескольких.

## Решение

Нумерация соответствует вопросам черновика.

- **В1, архитектура: вариант А, подписанное решение.** Брокер строит для каждого элемента очереди канонические байты одобрения (payload). Подписант получает их, разбирает строгим декодером, показывает каждое поле из результата разбора и после касания Touch ID подписывает ровно полученные байты ключом Secure Enclave. Брокер проверяет подпись над своими же байтами открытым ключом из нового перечня `approver_keys` и только потом выдаёт одноразовый токен. Проверка решения становится криптографической: uid одобряющего на хосте сам по себе больше не одобряет, а подпись становится доказательством решения в журнале.
- **В2, хранение ключа: блоб `dataRepresentation` в файле.** Без Apple Developer, без keychain access group, без нотаризации: подписант собирается и работает с подписью ad-hoc. Цена этого выбора записана в рисках: блоб доступен любому процессу того же пользователя на Mac. Переход на keychain возможен позже и не меняет ни протокол, ни брокер: для них ключ остаётся открытым ключом P-256 в allowlist.
- **В3, форма подписанта: приложение в строке меню macOS.** Не CLI. Приложение живёт в сессии пользователя с GUI, окно показа всплывает само при появлении элемента очереди. Так определено, какой процесс показывает окно, и подписант всегда работает в контексте, где LocalAuthentication доступна; вне GUI-сессии (SSH, демон) подписант отказывает, обходного пути нет.
- **В4, язык и место: Swift в отдельной папке `signer/`.** Своя сборка, свой macOS-раннер в CI. Go-часть в `src/` остаётся stdlib-only: проверка подписи это `crypto/ecdsa.VerifyASN1`, cgo к Security.framework в `src/` не появляется.
- **В5, политика аутентификации: только биометрия.** Ключ создаётся с `.privateKeyUsage` и `.biometryCurrentSet`; отката на пароль нет, Apple Watch не допускается. Смена набора отпечатков делает ключ непригодным; восстановление это новый ключ и новый анроллмент (В11). Пароль пользователя Mac вводится с клавиатуры и перехватывается кодом того же пользователя, биометрия нет: ради этого отличия и выбрана только биометрия.
- **В6, сроки задаёт только брокер.** Крайний срок решения и TTL токена входят в подписываемые байты; подписант своё время не ставит, часы Mac не участвуют в проверке. Брокер сверяет только собственные часы с собственными сроками и не выдаёт токен дольше подписанного TTL. Допуск расхождения часов не нужен, потому что сверять нечего.
- **В7, отказ подписанта это явный неподписанный `deny`.** Отмена, таймаут листа Touch ID, ошибка биометрии, непригодный ключ и невозможность показать поле целиком дают `deny` сразу, запрос снимается с очереди и не висит до `approval_timeout`. Подпись нужна только на одобрение: `deny` не даёт прав, подделка `deny` это лишь отказ в обслуживании, который и так доступен любому, кто может разорвать канал.
- **В8, транспорт прототипа: SSH к существующему каналу одобряющего.** Приложение запускает на хосте `tmb approve` в машинном режиме через SSH, получает очередь с байтами payload и отправляет `decide` с подписью. Листенеры брокера не меняются, ADR 0004 «канал одобряющего только локальный» остаётся буквально верным. Прямой TLS-листенер одобряющего в брокере это [#3](https://github.com/Vchekryzhov/tmb/issues/3) и отдельный ADR; payload переносим по любому каналу, поэтому смена транспорта криптографию не трогает.
- **В9, `require_signed_decision` глобально, без аварийного пути.** После включения неподписанный `decide` отклоняется кодом `signature_required` для любого одобряющего; `tmb approve` без подписи на хосте перестаёт одобрять. Аварийный путь не предусмотрен намеренно: он вернул бы ровно ту слабость, которую этот ADR устраняет. Требование формулируется как «подпись одним из ключей из `approver_keys`», тип ключа расширяем: запись в перечне несёт тип и открытый ключ, позже добавляются iPhone и FIDO-ключ (U2F/FIDO2) без переделки брокера.
- **В10, идентичность хоста в payload: имя из конфига плюс отпечаток серверного ключа брокера.** Оба поля входят в подписываемые байты, подпись для одного хоста не годится для другого. Подписант закрепляет список хостов на Mac при первом подключении (TOFU, как `known_hosts` в SSH): при смене отпечатка у известного имени подписант отказывает и предупреждает человека, молча список не обновляется.
- **В11, анроллмент ключа одобряющего вручную, по образцу ADR 0005.** Подписант создаёт ключ в Secure Enclave и экспортирует открытый ключ; человек переносит его на хост и добавляет запись в `approver_keys` конфига брокера, брокер перечитывает перечень по SIGHUP. Автоматического добавления нет. У человека может быть несколько ключей: Mac, запасной, позже iPhone или FIDO. Отзыв это удаление записи.
- **В12, realpath cwd и итоговое окружение входят в подписываемые байты обязательно.** Полный состав payload: версия формата и префикс домена; идентичность хоста (В10); id элемента очереди и полный хеш запроса; случайный challenge брокера на элемент; идентичность запросчика; целевой uid и имя пользователя; realpath исполняемого файла; упорядоченный argv; realpath cwd; итоговое окружение; nonce; время постановки в очередь; крайний срок решения; TTL токена. Человек подписывает то, что брокер выполнит, а не то, что агент прислал.

Инварианты совпадения показанного и подписанного, которые реализация обязана соблюсти: источник байтов один (брокер), подписант подписывает исходный массив байтов, а не свою сериализацию; подписант отклоняет payload, если повторная сериализация разобранной структуры не совпадает с полученными байтами; payload начинается с фиксированного префикса домена, поэтому подпись не годится ни для SSH, ни для другой версии формата; окно подписанта модальное для одного элемента, подпись привязана к элементу, показанному в момент касания; один `LAContext` на одну подпись с `invalidate()` сразу после.

## Последствия

Протокол (`src/internal/proto`):

- Новый тип `ApprovalPayload` с канонической сериализацией, префиксом домена, функцией построения байтов и строгим разбором с проверкой «сериализация разобранного равна исходным байтам». Тот же код использует фейковый подписант в тестах.
- `QueueItem` получает готовые байты payload (base64) рядом с текущими полями; подписанту не нужно собирать их из полей.
- `decide` получает `signature` (DER ECDSA) и `approver_key` (отпечаток SPKI, как в ADR 0005). Старый брокер отклоняет неизвестные поля (`DisallowUnknownFields`): старый брокер и новый подписант несовместимы, это ожидаемо для протокола без версии.

Конфиг и брокер (`src/cmd/tmb-broker`):

- Конфиг: `host_id`, `approver_keys` (тип ключа, открытый ключ или его отпечаток, имя), `require_signed_decision`. Перечень ключей перечитывается по SIGHUP, как `approver_uids`.
- Постановка в очередь генерирует challenge и строит payload; `decide` проверяет ключ по `approver_keys`, подпись над сохранёнными байтами и срок, и только потом передаёт решение в очередь. Новые коды отказа: `signature_required`, `signature_invalid`, `approver_key_unknown`, `decision_expired`.
- Выдача токена, погашение, закрепление exe и cwd не меняются. Подпись не заменяет погашение: токен по-прежнему одноразовый и гасится при предъявлении.
- Пока `require_signed_decision` выключен, брокер принимает и подписанные, и неподписанные решения и пишет в журнал, какое было; это и есть период перехода.

Клиент `tmb approve`: машинный режим вывода очереди и ввода подписанного решения для транспорта по SSH.

Журнал: событие `approval` получает тип и отпечаток ключа одобряющего и подпись; [docs/audit-schema.md](../audit-schema.md) и версия схемы событий меняются вместе. Запись с подписью это доказательство решения, которое можно перепроверить открытым ключом после факта.

CI и репозиторий: папка `signer/` со Swift-сборкой и macOS-раннером; N-серия получает сценарии с фейковым подписантом (ключ P-256 в файле, только в тестах): верная подпись, подпись чужого элемента, хоста и challenge, просроченное решение, неизвестный ключ, неподписанный `decide` при `require_signed_decision`, повтор подписи. Ручная проверка Touch ID на Mac идёт по протоколу в репозитории, без правок системного sudo и PAM.

Что остаётся за #3: прямой канал Mac к брокеру без SSH (TLS-листенер одобряющего или посредник), его аутентификация и анроллмент хостов с его стороны. Автономное разрешение без очереди (вариант Г) тоже там.

Словарь: термины «Доверенный подписант» и «Подписанное разрешение» в [CONTEXT.md](../../CONTEXT.md) переходят из будущих в действующие при реализации; «подписанное решение» здесь это `decide` с подписью над payload брокера, а не автономное разрешение из итогов грила.

## Отклонённые альтернативы

- **Б, Touch ID как гейт локального UI.** Брокер не меняется и не получает доказательства: кто получил канал одобряющего, одобряет без касания. Это слабость из [ADR 0001](0001-oneshot-ssh-certificates.md) пункт 3, и она не выполняет требование #2 «UI и биометрия не заменяют проверку».
- **В, аппаратный FIDO-ключ вместо Secure Enclave.** У U2F нет ни биометрии, ни показа, показ всё равно живёт в приложении на Mac; нужен `libfido2` или своя реализация CTAP поверх HID. Не отвергнут навсегда: расширяемый тип ключа в `approver_keys` (В9) оставляет FIDO как второй ключ позже.
- **Г, подписанное разрешение без очереди.** Противоречит ADR 0004 и требует передать запрос подписанту в обход брокера: показ строился бы из данных агента, а не из разрешённых брокером realpath и итогового окружения. Остаётся будущим вариантом для #3.
- **Ключ в keychain access group.** Требует бандла с provisioning profile, аккаунта Apple Developer, Developer ID и нотаризации для распространения. Цена не оправдана на этапе прототипа; путь перехода открыт (В2).
- **CLI вместо приложения.** CLI не владеет окном и не живёт в GUI-сессии постоянно; окно показа пришлось бы заводить отдельно (В3).
- **Пароль как откат биометрии, Apple Watch.** Пароль вводится с клавиатуры и перехватывается кодом пользователя; Apple Watch расширяет круг устройств, которым доверяется касание (В5).
- **Время подписи от подписанта.** Потребовало бы сверять часы Mac и хоста и выбирать допуск; брокер и так владеет обоими сроками (В6).
- **Молчаливый отказ (запрос истекает сам).** Держит запрос в очереди до `approval_timeout` без пользы; явный `deny` быстрее и попадает в журнал как решение (В7).
- **Аварийный неподписанный `tmb approve`.** Возвращает слабость канала, ради устранения которой и принят этот ADR (В9).

## Остаточные риски

- **Root на Mac или подмена приложения подписанта.** Ключ не покидает Secure Enclave и без касания подписи нет, но root управляет показом и числом подписей за касание и может подменить байты между показом и подписью. Риск принимается: компрометация Mac равна компрометации одобряющего. Смягчение, второе устройство (iPhone) с требованием двух подписей в политике брокера, это будущая работа поверх расширяемого типа ключа.
- **Код того же пользователя на Mac с ключом-блобом.** Может загрузить блоб и попросить подпись над своими данными; системный лист Touch ID покажет имя этого процесса и его строку причины, но человек может коснуться не глядя. Смягчение: keychain access group (В2, позже) и привычка читать лист.
- **Социальная инженерия.** Агент присылает правдоподобную вредную команду, человек её одобряет. Подпись доказывает согласие человека и ничего не говорит о безвредности команды; защита это показ каждого аргумента отдельно с экранированием управляющих и не-ASCII символов.
- **Скомпрометированный брокер.** Показывает подписанту одно, выполняет другое. Вне модели: брокер и есть исполнитель с root на хосте.
- **Отказ в обслуживании по каналу.** Сеть или код с uid одобряющего шлёт `deny` или рвёт SSH, и одобрение не доходит. Прав это не даёт, риск принимается.

## Открытые вопросы

- Точный формат записи в `approver_keys` (тип, кодирование открытого ключа, имя) и формат экспорта открытого ключа подписантом: решаются при реализации вместе с ADR 0005-стилем отпечатка.
- Поведение подписанта при нескольких хостах и нескольких элементах одновременно (очередь окон, порядок): UX, не безопасность.
- Политика «две подписи с разных устройств» и тип ключа iPhone: отдельный ADR после прототипа.
