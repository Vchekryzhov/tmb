# RESEARCH: NVIDIA OpenShell as TMB sandbox layer

> Historical research snapshot (2026-10-09), not the current implementation guide. OpenCode is the example agent in the researched tutorial; the TMB protocol does not depend on that agent. [ADR 0003](../../docs/adr/0003-sandbox-transport-tcp-mtls.md) selects OpenShell + TCP/mTLS with length-prefixed JSON, not MCP. The implemented rig and its limits are described in [VERDICT-OPENSHELL.md](../../VERDICT-OPENSHELL.md).

**Verdict: OpenShell exists, is real, active, and fits the TMB PoC.** Recommended: wrap OpenCode in OpenShell; expose the TMB broker either as (A) a single bind-mounted Unix socket (direct, unmediated) or, cleaner, (B) a single TCP/MCP endpoint allowed by exactly one `network_policies` rule (mediated, audited, hot-reloadable). TMB approval stays separate from OpenShell's network-policy approvals.

## Q1. Can an interactive CLI agent (OpenCode) run inside?
**Yes: OpenCode is the official "first agent" tutorial.** `openshell sandbox create -- <cmd>` runs any CLI as the sandbox's canonical main process (streamed output, exit status); with no command it starts a login shell. `sandbox connect` attaches to the main process (replays ≤1 MiB, reattach after disconnect); `sandbox exec -n X --tty -- /bin/bash` opens an independent shell. TUI: `openshell term`.

## Q2. Sandbox ↔ host interaction model (what escapes by design)
Each sandbox = container (Docker/Podman) or VM (MicroVM) with **all direct egress denied**: Docker/Podman workload runs with networking off; VM guest has no network device. The **only** egress is a mutually-authenticated mediated channel to a trusted **supervisor** (Unix socket for Docker/Podman, vsock for VM, mTLS TCP for K8s); TCP opens + DNS are intercepted via seccomp user-notify and policy-checked by the supervisor/L7 proxy (TLS-inspected, per binary/host/port/method/path). Inside: one non-root UID, no Linux capabilities, Landlock filesystem rules.
- Architecture: [architecture.mdx#L13-L16](https://github.com/NVIDIA/OpenShell/blob/fe2dd3e/docs/about/architecture.mdx#L13-L16), boundary detail [#L46-L52](https://github.com/NVIDIA/OpenShell/blob/fe2dd3e/docs/about/architecture.mdx#L46-L52), mediated channel [#L55-L64](https://github.com/NVIDIA/OpenShell/blob/fe2dd3e/docs/about/architecture.mdx#L55-L64), "only allowed egress path" [#L90-L92](https://github.com/NVIDIA/OpenShell/blob/fe2dd3e/docs/about/architecture.mdx#L90-L92), per-runtime fence table [#L100-L105](https://github.com/NVIDIA/OpenShell/blob/fe2dd3e/docs/about/architecture.mdx#L100-L105)
- Escapes **by design**: policy-approved TCP (with credential injection via providers), explicit mounts (volume/tmpfs; bind gated, see Q3), CLI file upload/download, host→sandbox port forwards and gateway-published service URLs, SSH connect via gateway. Credentials are never stored inside the sandbox: injected only into approved requests ([architecture.mdx#L33-L35](https://github.com/NVIDIA/OpenShell/blob/fe2dd3e/docs/about/architecture.mdx#L33-L35)).
- **AF_UNIX is explicitly allowed** inside the sandbox (seccomp filter allows AF_UNIX, AF_NETLINK(route only), brokered AF_INET/6): [best-practices.mdx#L223](https://github.com/NVIDIA/OpenShell/blob/fe2dd3e/docs/security/best-practices.mdx#L223). Unix-socket traffic is **not** mediated by the network policy engine (it intercepts TCP/DNS only: [architecture.mdx#L74](https://github.com/NVIDIA/OpenShell/blob/fe2dd3e/docs/about/architecture.mdx#L70-L79)).

## Q3. Restrict to exactly ONE Unix socket / IPC endpoint?
**Yes, two ways:**
- **(A) Bind-mount the single socket file** into the sandbox: Docker/Podman `mounts: [{"type":"bind","source":"/run/tmb.sock","target":"/run/tmb.sock"}]` via `--driver-config-json`. Requires `enable_bind_mounts = true` + disabling resource admission (docs explicitly warn bind mounts bypass workspace isolation and filesystem policy). `filesystem_policy` denies any path not listed (≤256 paths), so nothing else on host FS is visible. Socket connect then works by standard Linux DAC (socket file perms must admit the sandbox UID: set group/chmod accordingly). *Socket-bind-mount specifically: unverified in docs (bind of host paths is documented; sockets follow standard Linux semantics; confirm in PoC).* Source: [runtimes.mdx#L139-L173](https://github.com/NVIDIA/OpenShell/blob/fe2dd3e/docs/how-it-works/sandboxes/runtimes.mdx#L139-L173), [schema.mdx#L40-L56](https://github.com/NVIDIA/OpenShell/blob/fe2dd3e/docs/how-it-works/policies/schema.mdx#L40-L56)
- **(B) TCP endpoint + exactly one network rule** (cleaner, audited): `network_policies` is deny-by-default; one rule = one endpoint (host:port, per-method/path for HTTP/MCP) × listed binaries. If TMB speaks MCP-over-HTTP, OpenShell natively tracks/diagnoses such tool-server endpoints. Rules are hot-reloadable. Prover flags private-address endpoints as risky but they can be explicitly allowed. Source: [network-rules.mdx#L11-L45](https://github.com/NVIDIA/OpenShell/blob/fe2dd3e/docs/how-it-works/policies/network-rules.mdx#L11-L45), tool-server status [sandboxes/overview.mdx#L706-L731](https://github.com/NVIDIA/OpenShell/blob/fe2dd3e/docs/how-it-works/sandboxes/overview.mdx#L706-L731)

## Q4. Built-in approval / policy-proposal mechanisms
- **Policy Advisor** (off by default): blocked agent gets deny reasons + `http://policy.local` API to propose the network rule it needs; every proposal waits for **human review** (`openshell rule get --status pending` / `rule approve` / `rule reject`); optional auto-approve gated by **formally verified risk checks** (policy prover). Network rules only: cannot touch filesystem/Landlock/process (static at start). Source: [advisor.mdx#L11-L59](https://github.com/NVIDIA/OpenShell/blob/fe2dd3e/docs/how-it-works/policies/advisor.mdx#L11-L59), approve/reject [#L114-L136](https://github.com/NVIDIA/OpenShell/blob/fe2dd3e/docs/how-it-works/policies/advisor.mdx#L114-L136)
- **Gateway Interceptors**: external gRPC service can validate/modify every control-plane API write (e.g., force an approved policy onto new sandboxes, reject weakening); endpoints incl. **`unix://`**. Natural integration point if TMB wants to govern sandbox lifecycle too. Source: [gateway-interceptors.mdx#L10-L24](https://github.com/NVIDIA/OpenShell/blob/fe2dd3e/docs/extensibility/gateway-interceptors.mdx#L10-L24), unix:// [#L98](https://github.com/NVIDIA/OpenShell/blob/fe2dd3e/docs/extensibility/gateway-interceptors.mdx#L98)
- **These are network/governance approvals, not per-tool-call execution approvals.** TMB's human-in-the-loop for privileged ops should stay in TMB (the agent reaches TMB through the single endpoint from Q3); optionally TMB appears as a gateway interceptor. Reuse, don't duplicate: OpenShell's advisor UX is a good pattern reference.

## Q5. OpenShell as pure isolation + TMB as separate privileged broker?
**No architectural conflict.** OpenShell's own architecture assumes the agent is untrusted and everything valuable (credentials, decisions) lives outside the boundary, exactly TMB's model. TMB = root host service; sandbox sees only the one endpoint (Q3). Caveats: (1) route A weakens OpenShell's mount admission by design, acceptable for PoC if that socket is the *only* mount; (2) unix-socket traffic is unmediated/unlogged by OpenShell, so auditing of the TMB channel must live in TMB; (3) OpenShell 0.1.x API churn is real (e.g., `--from` breaking change), so pin versions.

## Recommendation for the PoC
1. **Use OpenShell, not a plain container**: it gives the deny-by-default egress, per-binary identity, Landlock FS, non-root, and deny diagnostics for free; OpenCode is its documented first-class agent.
2. **Socket passthrough**: prefer **(B) TCP/MCP endpoint + single network rule** (audited, hot-reloadable, no admission weakening) for the first cut; fall back to **(A) bind-mounted Unix socket** if TMB must stay Unix-socket-only (accept unmediated channel + `enable_bind_mounts` tradeoff).
3. **Keep TMB approvals in TMB**; treat OpenShell policy advisor/prover as the mechanism for *network* scope only. Optionally later: TMB as gateway interceptor.
