# VERDICT — вердикт прототипа sudo-интеграции (THROWAWAY)

Дата прогона: 2026-10-08. Хост: macOS arm64, Docker 29.6.1. Лог: `last-run.log`
(сгенерирован `./run.sh`; ключевые строки процитированы ниже дословно).

## Ответ на вопрос прототипа

**Да.** Подписанное одноразовое разрешение приводится в исполнение настоящим sudo
в одноразовых непривилегированных контейнерах, при сохранении политики sudoers и
обычного парольного sudo человека, с атомарным переживает-перезапуск погашением
строго до запуска. Все 44 проверки фазы 1 и 4 проверки фазы 2 прошли (см. таблицу).
Победившая точка интеграции — **(a) python approval-плагин sudo**, с одной
развилкой про сборку sudo (ниже).

## Сравнение точек интеграции (требование issue #1)

| Критерий | (a) Python APPROVAL-плагин | (b) NOPASSWD-диспетчер | Python POLICY-плагин |
|---|---|---|---|
| Роль sudoers | **остаётся политикой**: плагин вызывается ПОСЛЕ решения sudoers и может только наложить вето | sudoers видит только обёртку-диспетчер, целевую команду не видит | **заменяет sudoers** — единственный policy-плагин |
| Совместимость с контрактом | соответствует: «шлюз встроен в sudo, одобренные программа и argv передаются фактическому выполнению без изменений» | частично: программа и argv идут через `os.execv` (одно исполнение), но sudoers не видит цель | нарушает контракт «слепая замена sudoers недопустима» |
| Обычный парольный sudo человека | не затронут (плагин scoped на agent-пользователя; проверено) | не затронут | вытесняет общий путь |
| stdin закрыт для потомка | конвенция вызывающей стороны (проверено пробой) | принудительно диспетчером (`dup2(/dev/null)`) | — |
| Что видит sudo в запуске | точные program+argv (сравниваются с подписанными) | только диспетчер и base64-конверт | определяет всё сам |
| Доступность в дистрибутивах | пакеты НЕ собирают python-плагин (см. отрицательный результат) — нужна сборка sudo из исходников с `--enable-python` | работает на любом sudo | та же проблема сборки + замена sudoers |
| Вердикт | **ВЫБРАН** (экспериментальный победитель) | запасной, протестирован (сценарий 9) | **отклонён по контракту**, не реализовывался |

Политика-плагин отклонён не эмпирически, а по договорённости грила и issue #1:
единственный policy-плагин подменяет sudoers, что прямо запрещено («одно одобрение
сами по себе не заменяет существующий парольный шаг; слепая замена sudoers
недопустима»), и ломает обычный путь человека.

Диспетчер (b) сохранён как запасной и полностью работоспособен (одиночное исполнение
через `os.execv`, атомарное погашение, гонки, истечение), но его трейдофф показан
вживую: валидно подписанное разрешение на `/usr/local/tmb/bin/dangerous` — команду,
которой нет в sudoers, — через диспетчер **выполняется**:

```
[sudo tmb-dispatch out] DANGEROUS executed as euid=0 argv=['/usr/local/tmb/bin/dangerous', 'ran', 'via', 'dispatcher']
[PASS] 9b: TRADEOFF proven - sudoers sees only the dispatcher, so a valid permission for a non-sudoers command runs
```

Через хук (a) та же валидная подпись на той же команде отклоняется самим sudoers
до вызова плагина (в audit нет строки `check`):

```
[sudo] exit=1
[sudo err] sudo: a password is required
[PASS] 6: sudoers rejects forbidden command despite valid permission
[PASS] 6: approval plugin never consulted (policy rejected first)
```

## Версии и механика (проверено в контейнере)

```
[sudo binary] /usr/local/bin/sudo
[sudo] Sudo version 1.9.17p1
[sudo] Configure options: --enable-python --sysconfdir=/etc --without-sendmail
[dpkg (distro baseline)] python3-cryptography=41.0.7-4ubuntu0.4 sudo=1.9.15p5-3ubuntu5.24.04.4
[python=3.12.3 cryptography=41.0.7]
[sudo.conf active lines] ['Plugin python_approval /usr/local/libexec/sudo/python_plugin.so ModulePath=/usr/local/tmb/lib/tmb_approval.py ClassName=TmbApprovalPlugin']
```

Регистрация плагина подтверждается самим sudo (`sudo -V` от root):

```
Python approval plugin (API 1.0): TmbApprovalPlugin (loaded from '/usr/local/tmb/lib/tmb_approval.py')
TMB approval plugin (PROTOTYPE, throwaway)
```

API approval-плагина: `check(command_info, run_argv, run_env)` вызывается после
`check_policy` sudoers; отказ — `raise sudo.PluginReject(...)` или `return sudo.RC.REJECT`
(man sudo_plugin_python, сверено с документацией sudo.ws и поведением в контейнере).
Идентификация вызывающего — `user_info` конструктора плагина (`user=agent`), run-as —
из `command_info` (`runas_user=`).

## Отрицательный результат №1: пакеты дистрибутивов не несут python-плагин

Проверено во время работы над прототипом (контейнеры `docker run --rm`):

| Дистрибутив | sudo | `python_plugin.so` в пакете |
|---|---|---|
| ubuntu:24.04 | 1.9.15p5 | **нет** (сборка без `--enable-python`) |
| debian:trixie | 1.9.16p2 | **нет** |
| fedora:41 | 41.x | **нет** |
| alpine:3.21 | 1.9.x | **нет** |

Следствие: хук (a) сегодня требует сборки sudo из исходников (официальный tarball
sudo.ws, `./configure --enable-python`, что и делает Dockerfile прототипа). Это не
блокер для эксперимента, но это реальное ограничение развёртывания: до появления
дистрибутивных сборок с python-плагином приёмный хост должен собирать sudo сам, либо
сидеть на хуке (b) с его трейдоффом. Если бы сборка была невозможна, решением по
заданию был бы диспетчер (b) с зафиксированным трейдоффом.

Отрицательный результат №2 (мелкий): имя файла у апстримного апплага —
`python_plugin.so` (ставится в `/usr/local/libexec/sudo`), а не
`sudo_plugin_python.so`, как называют его некоторые пакеты/доки; первая попытка
регистрации по «дистрибутивному» имени предсказуемо упала (`cannot open shared
object file`) — учтено в Dockerfile и в этом вердикте.

## Ограничения и нерешённое

- **Однохостовый тест**: контейнер Linux на docker/macOS; заявлений о DSM, Synology,
  других платформах нет.
- **Touch ID/живой подписант вне прототипа**: фейковый подписант — локальная команда
  с настоящим тестовым ключом ed25519; транспорт и Mac — issues #2/#3.
- **stdin**: в approval-режиме закрытие stdin — конвенция вызова (sudo у нас всегда
  запускается с `</dev/null`, проба это фиксирует); принудить stdin плагин approval
  не может по API. В диспетчере — принудительно.
- **env/cwd** — вне scope, гарантий нет.
- **Нет запросов состояния и восстановления**: после неоднозначного сбоя новое
  одобрение может повторить уже совершённое действие; ошибка запуска не возвращает
  разрешение.
- **Approval-плагин глобален для sudo**: скоупинг «только agent-пользователь» —
  логика самого плагина (проверка `user_info.user`), а не свойство sudo; это
  проектное решение, которое надо пронести в ADR.
- **Подписант и ключ в одном контейнере**: тестовая приватная ручка лежит рядом с
  проверяющим — в реальной схеме подписант на Mac и ключ на приёмный хост не
  попадает никогда.
- TTL 60 с не выжидается реально: валидные подписи короткие, истёкшие подписываются
  напрямую с прошедшим `expires_at`.

## Что дальше (вход для ADR и issues #2/#3)

Точка интеграции подтверждена: approval-плагин sudo поверх нетронутых sudoers, приём
разрешения через env (`env_keep TMB_PERMISSION` в прототипе; транспорт — отдельное
решение), погашение `O_EXCL`+fsync в отдельном состоянии. Для продвинутой версии
нужно решить: сборка/доставка sudo с `--enable-python` на приёмных хостах (или
фолбэк на диспетчер с осознанным трейдоффом), анроллмент доверия к ключу подписанта,
транспорт запроса к подписанту и настоящее Touch ID-ядро (#2, #3).
