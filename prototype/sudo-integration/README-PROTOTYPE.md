# PROTOTYPE — THROWAWAY (одноразовый прототип, не продукт)

Этот каталог — выбрасываемый прототип по [issue #1](https://github.com/Vchekryzhov/tmb/issues/1).
Он отвечает на **один вопрос проектирования**: можно ли вменяемое одноразовое подписанное
разрешение приводить в исполнение силами **настоящего sudo** в одноразовых непривилегированных
Linux-контейнерах, сохранив действующую политику sudoers и обычный парольный sudo человека,
с атомарным, переживает-перезапуск погашением разрешения строго до запуска.

Ничего здесь не является производственным инструментом, установщиком или системой тестирования
продукта. Прогнавшийся сценарный раннер и есть демо. Результаты и обоснование выбора точки
интеграции — в [VERDICT.md](VERDICT.md).

## Отступление от навыка «prototype»

Навык прототипирования предлагает две формы: логическая демонстрация одним HTML-файлем или
UI-вариации. **Обе не подходят**: вопрос — про механику реального sudo (плагины, sudoers,
атомарное погашение, гонки), которую HTML не моделирует. Поэтому форма — контейнерный
сценарный раннер, применяющий универсальные правила навыка к этой форме:

- одноразовость помечена везде (имена `tmb-proto-*-wipe-me`, баннеры PROTOTYPE);
- запуск одной командой без раздумий: `./run.sh`;
- никакого персистентного состояния, кроме исследуемого scratch-состояния
  (том `tmb-proto-state-wipe-me` — сам предмет проверки — погашения);
- без полировки: без тест-фреймворков, CI и обработок ошибок сверх необходимых для запуска;
- полное состояние (JSON разрешения, каталог погашений, коды возврата, ключевые строки
  вывода) печатается после каждого сценария.

## Как запустить

Требования: рабочие `bash` и `docker` (проверено на Docker 29.6.1, macOS arm64;
образ `ubuntu:24.04` arm64). Интернет нужен для `apt` и скачивания исходников sudo
с sudo.ws при первой сборке образа.

```
cd prototype/sudo-integration
./run.sh
```

`run.sh` идемпотентен: перестраивает образ (кэш Docker ускоряет повторные запуски),
создаёт свежий том состояния и одноразовый контейнер `tmb-proto-container-wipe-me`,
прогоняет матрицу сценариев (фаза 1), перезапускает контейнер (`docker restart`),
прогоняет фазу 2 (переигровка после рестарта) и удаляет контейнер и том. Полный лог
остаётся в `last-run.log`. Код возврата ненулевой, если хоть одна ожидаемая-отказ
проверка неожиданно прошла или хоть одна ожидаемая-успех провалилась.

Полный прогон: ~47 проверок в 10 сценариях (0–9) + 4 проверки фазы 2; после первой
сборки образа матрица укладывается в ~15 секунд.

## Что происходит внутри

- Образ: `ubuntu:24.04` + **sudo 1.9.17p1, собранный из официального tarball с
  `--enable-python`** (пакеты дистрибутивов не собирают python-плагин — см. VERDICT),
  python3 + `cryptography` (реальный ed25519), тестовые пользователи `agent`
  (путь TMB, NOPASSWD) и `viktor` (человек, классический парольный sudo).
- Разрешение: JSON `{request_id, hostname, runas_user, program, argv[], issued_at,
  expires_at}`, канонизируется и подписывается ed25519 тестовым ключом, который
  генерируется **заново на каждый прогон внутри контейнера**.
- Погашение: claim-файл через `O_CREAT|O_EXCL` + `fsync` файла и каталога в
  `/var/lib/tmb-proto/redeemed` (том Docker) — строго до запуска.
- Фейковый подписант: локальная команда `/usr/local/tmb/bin/fake-signer`,
  режим `approve | deny | timeout` в `/usr/local/tmb/etc/signer-mode`.
- Хук (a): python-плагин `TmbApprovalPlugin` (approval-плагин sudo) в `/etc/sudo.conf`;
  хук (b): диспетчер `/usr/local/tmb/bin/tmb-dispatch` (NOPASSWD-обёртка) — оба
  протестированы, см. VERDICT.md.

## Как стереть всё

`run.sh` сам удаляет контейнер и том. Добить вручную:

```
docker rm -f tmb-proto-container-wipe-me
docker volume rm tmb-proto-state-wipe-me
docker rmi tmb-proto:sudo-integration
rm -f last-run.log
```

## Изоляция (жёсткие границы)

Только одноразовые непривилегированные контейнеры: без `--privileged`, без проброса
`docker.sock`, без монтирования путей хоста (единственный bind — контекст сборки этого
каталога; состояние — именованный том). Тестовые ключи/доверие/конфиги/состояния живут
только в контейнере и томе. Хост macOS не изменяется; sudoers/PAM/sshd реальных машин
не трогаются. Файлов за пределами `prototype/sudo-integration/` прототип не создаёт и
не меняет; коммиты не делаются.

## Чего прототип НЕ обещает

- Никаких заявлений о совместимости с DSM и о живом сценарии Mac/Touch ID
  (подписант реальный — issue #2, транспорт удалённого одобрения — #3).
- Никаких гарантий по env и cwd: они вне scope.
- `stdin` закрыт для запущенного процесса: в режиме approval-плагина это конвенция
  вызывающей стороны (проверяется пробой), в режиме диспетчера — принудительно
  самим диспетчером (см. VERDICT).
- Запросов состояния и восстановления нет: после неоднозначного сбоя новое одобрение
  может привести к повтору уже совершённого действия (задокументировано, не «чинится»).
- Ошибка запуска не возвращает разрешение в оборот.
